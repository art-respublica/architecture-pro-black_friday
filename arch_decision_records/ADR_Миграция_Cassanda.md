### <a name="_qmphm5d6rvi3"></a>**Решение**

Для решения проблем в "чёрную пятницу", обусловленные перераспределением данных между узлами и задержками в обработке запросов в пик нагрузки,
то есть проблемами «горячих» шардов в «чёрную пятницу», предлагается изменить архитектуру решения. 
А именно использовать для некоторых частей магазина БД Cassandra.
Cassandra изначально проектировалась для таких нагрузок: запись с любой ноды (leaderless), 
отсутствие единой точки отказа и линейное масштабирование без болезненного перераспределения данных.

|:-----------------:|:---------------------------------------------------------------------------|:-------------------------------------------------------|:---------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------|

Это усложняет связь заказ-товары.                                                                                      |

#### Рекомендации по миграции (что имеет смысл перенести):
1. Список товаров - 70% запросов на получение
2. Историю заказов — append-only, временные ряды
3. Пользовательские сессии — высокая скорость чтения с автоматическим удалением.

#### Модель данных в Cassandra
1. Список товаров.
Partition key = category — все товары одной категории в одной партиции. Это позволит эффективно листать товары внутри категории.
Clustering key = product_id — сортировка по ID.
Денормализация — все данные товара в одной строке, никаких joins.
Есть риск горячей партиции для некоторых категорий. В этом случае нужно распределить данные этой категории по нескольких партициям с помощью хешированного шардирования.

2. История заказов
Partition key = (user_id, order_month) — комбинация пользователя и месяца заказа. Это гарантирует, что заказы одного пользователя за разные месяцы попадают в разные партиции, исключая перегрузку.
Clustering key = order_date DESC — самые свежие заказы читаются первыми.
Денормализация: items хранит весь состав заказа в JSON-строке. Это необходимо, так как Cassandra не умеет делать JOIN с таблицей товаров.

3. Пользовательские сессии
Partition key = session_id — равномерное распределение, каждая сессия в отдельной партиции.
TTL на уровне таблицы — Cassandra автоматически удалит сессию через 24 часа, не нагружая администратора.

#### Стратегии обеспечения целостности данных

Cassandra имеет три механизма синхронизации реплик:

|     **Механизм**      | **Когда срабатывает**               | **Нагрузка**  | **Задержка**     |
|:---------------------:|:------------------------------------|:--------------|:-----------------|
|    Hinted Handoff     | При временной недоступности ноды    | Низкая        | Секунды / минуты |
|      Read Repair      | При чтении (вероятностно или по CL) | Средняя       | Моментально      |
| Anti-Entropy Repair   | Ручной запуск                       | Очень высокая | Часы / дни       |

1. Список товаров.
Стратегия: Read Repair (read_repair_chance = 0.1)
Обоснование: Цены и описания товаров обновляются нечасто. Если пользователь при чтении получит устаревшую цену (отличие на одной реплике), 
Read Repair исправит это для 10% запросов. Этого достаточно, чтобы данные оставались консистентными без постоянной нагрузки на кластер.
Hinted Handoff: Включён. Если нода с каталогом упала, координатор сохранит хинты и доставит обновления, когда она вернётся.

2. История заказов
Стратегия: Полное отключение Read Repair + периодический Anti-Entropy Repair (раз в неделю)
Обоснование: История заказов — append-only (только вставка, никогда не обновляется). Если данные потерялись на одной реплике, 
они не восстановятся через Read Repair, так как их там никогда не было. Единственный способ наверстать — полный Anti-Entropy Repair в пределах gc_grace_seconds (обычно 10 дней).
Hinted Handoff: Критически важен. При падении ноды во время «чёрной пятницы» хинты сохранят заказы и доставят их позже.

3. Пользовательские сессии
Стратегия: Hinted Handoff только для записи, Read Repair выключен
Обоснование: Сессии живут недолго (TTL 24 часа). Если сессия прочитана с устаревшей реплики — пользователь просто пересоздаст сессию (логаут/логин). Целостность не критична.
Anti-Entropy Repair: Не требуется, так как данные сами удаляются по TTL, а ремонт всего кластера раз в неделю будет воскрешать «удалённые» строки (tombstone resurrection)
