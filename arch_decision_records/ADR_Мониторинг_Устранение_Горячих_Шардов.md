### <a name="_qmphm5d6rvi3"></a>**Решение**

Из-за выбора верхнего ключа шардирования товаров по category_id есть риск превышения количества элементов коллекций товаров одних категорий в 3-4 раз по сравнению с другими категориями. 
Из-за этого скорость получения товаров из этих шардов может катастрофически замедлиться. Шард станет "горячим".

Для предотвращения таких ситуация предлагается последовательность шагов: 
1. Диагностика (мониторинг метрик)
2. Реагирование (устранение)
3. Профилактика.

#### Метрики мониторинга
1. Количество операций в секунду. 
   Нужно добавить метрику для операций: insert, query, update, delete (CRUD) для каждого шарда.
   Если на шарде метрика будет стабильно выше остальных в 2-3 раз,- это кандидат на превращение в "горячий" шард.
2. Размер очереди. Метрика `globalLock.currentQueue.total`
   Высокие значения говорят, что шард не справляется с нагрузкой.
3. Задержки. Метрика `opLatencies`
   Высокие значения говорят, что шард не справляется с нагрузкой.
4. Статистика коллекции. Метрики `db.collection.getShardDistribution()`
   Если количество запросов к шардам имеет явный дисбаланс, то шард с аномальным превышением количества запросов 
   - это кандидат на превращение в "горячий" шард.
5. Отношение размера шардов к лимиту. Если шард приближается к лимиту - это кандидат на превращение в "горячий" шард.

#### Методы реагирования (устранения)
1. Ручное разделение шардов с помощью команды `sh.splitAt()`
2. Перемещение элементов из "горячего" шарда по другим шардам с помощью скриптового вызова команд `moveChunk`

#### Методы профилактики
1. Разбитие конкретного ключа шардирования на несколько значений с меньшим количеством элементов. 
   Данные перераспределяться по шардам автоматически с течением времени.
2. Архитектурный пересмотр выбора ключа шардирования с переходом на хешированное шардирование.
